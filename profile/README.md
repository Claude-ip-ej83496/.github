<p>「住宅 IP 用久了会掉速」这句话本身太粗，粗到没法排查。实际上一篇文章里说的掉速，可能来自完全不同的五个位置：上游带宽被挤、协议握手排队、会话没有保活、备用线路切换失败、业务侧的等待时间没有上限。每一层的表现都像「慢」，处理方式却完全相反。这篇把这条链路从底往上拆成五层，逐层给出可观测的指标和判定阈值，最后给一个固定顺序的排查路径，避免一上来就换服务商。</p>

<h2>一、掉速是五层问题叠加，不是一次故障</h2>
<p>先把「慢」这个感受翻译成可测的数字。同样一句「卡了」，在日志里可能是首字节三秒、可能是连接建立失败重试、也可能是请求成功但结果返回不全。</p>
<h3>五个层次分别负责什么</h3>
<p>带宽层负责吞吐上限；协议层负责连接建立与复用；会话层负责连接存活；调度层负责在多条线路之间分配并发；业务层负责超时与重试策略。任何一层出问题，用户侧看到的都是「页面转圈」，只有把指标分层采集，才能定位到具体是哪一层。</p>
<h3>先用三个数字做初筛</h3>
<p>首字节时间（TTFB）、连接建立耗时、以及单位时间内的失败率。TTFB 稳定在五百毫秒内、失败率低于百分之一，说明链路本身没问题，慢在业务侧；TTFB 忽高忽低且失败率上升，就要往协议或带宽层查。</p>

<h2>二、带宽与上游层：先排除最粗的那一段</h2>
<p>这一层最容易被忽略，因为它不在你的控制范围内，却是很多「用一段时间就变慢」的真正原因。</p>
<h3>家宽上行是共享的</h3>
<p>原生家宽出口的上行带宽取决于所在小区的实际负载，晚间高峰（当地十九点到二十三点）普遍会下降，同一段被多个买家共用时更明显。判断方法：连续七天在同一时刻跑 <code>curl -w</code> 记录下载速率，若曲线在固定时段下凹，那就是上游拥塞，不是你的配置问题。</p>
<h3>把长任务挪出高峰</h3>
<p>批量任务用不到实时响应，把窗口挪到当地凌晨，速率通常能回升三到五成。这一步不需要任何成本，却常被跳过。若业务必须跑在高峰，就得在采购时明确要求独享带宽或提高上限，而不是指望调优。</p>

<h2>三、协议与并发层：连接数堆上去反而更慢</h2>
<p>很多人遇到慢的第一反应是把并发从十调到五十，结果更慢。原因是住宅线路的并发承载能力远低于机房。</p>
<h3>并发是有上限的</h3>
<p>单条家宽线路同时维持的 TCP 连接数超过一定量之后，握手排队会拉长每一个请求的建立时间。经验值：单条住宅出口的并发请求控制在五到十之间比较稳，超过二十失败率明显上升。这个数字要按自己的线路实测，不同运营商差异很大。</p>
<h3>复用比新建划算</h3>
<p>开启 HTTP 长连接复用，把一次会话内的请求压在同一个连接上，可以省掉大量握手。代价是连接长时间占用，需要配合保活。若客户端不支持复用，至少把连接池上限设小，让排队发生在本地而不是在链路上。</p>
<p>协议选择也要看场景：需要低延迟交互的，走 UDP 系的协议更顺；需要稳定传输大文件的，TCP 更可控。两者混用时注意端口不要争抢，最好分开配置。</p>

<h2>四、会话与切换层：丢一条线为何会牵连整个后台</h2>
<img src="/tp.png" alt="Claude住宅IP多线路会话保活与备用线路监测">
<p>这是「一条线路牵连全盘」的技术根源。问题不在线路本身，而在切换机制缺失或切换方式粗暴。</p>
<h3>没有保活，连接会被中间设备回收</h3>
<p>家宽线路经过 NAT 设备，空闲连接通常在三到十分钟被回收。如果业务侧不知道连接已断，仍往旧连接写数据，表现就是「发出去没回应、等超时」。开启应用层心跳，间隔设在六十到一百二十秒，可以让连接在回收前被刷新。</p>
<h3>切换要保留会话上下文</h3>
<p>最简单也最常见的错误做法是：检测到线路断开，直接换一条新出口重连。此时新出口的地址变了，平台侧看到的是一次异地登录，于是触发验证，业务上表现为「切了线反而全挂」。正确做法是把切换粒度放在连接层而不是账号层，新连接沿用同一出口段，或者在同一段内换端口。</p>
<h3>备用线路要预先热备</h3>
<p>冷备的切换时间是分钟级，热备是秒级。热备意味着备用线路已经建好连接、已经通过鉴权、只等主线路失效就接管。配置上通常表现为一个健康检查加一个优先级列表，主线路连续三次探测失败后提升备用。</p>

<h2>五、监控与排查顺序：按层往下走，不要跳步</h2>
<p>排查最怕的是同时改三处，改完不知道是哪一处起了作用。固定顺序能省掉大量试错。</p>
<h3>先看端到端成功率，再看单层指标</h3>
<p>成功率跌破阈值，才往下拆。拆的顺序是带宽、协议、会话、切换、业务，从前到后。每层只看一个指标，符合阈值就往下走，不符合就停在这一层处理，处理完再重新测端到端。</p>
<h3>把切换记录当一等公民</h3>
<p>很多团队只记录成功请求，不记录切换事件。结果是「昨天慢了半小时」这种描述无法复盘。建议把每次主备切换的时间、原因、耗时、切换后十分钟内的失败率都落盘，一周回看一次，能提前发现线路劣化的趋势。</p>
<h3>什么时候该认定是供应商问题</h3>
<p>三条同时成立：同段其他线路同步变差、你自己的配置一周内没有改动、换一条不同段的新线路后指标恢复正常。三条都满足，才值得去找供应商交涉，否则多半是自己的调度或业务侧设置。</p>

<h2>常见问答</h2>
<h3>掉速一定是线路问题吗？</h3>
<p>答：不一定，而且多数时候不是。业务侧的超时设置、重试逻辑、并发调度都会表现为慢。先测端到端成功率，再分层拆，能避免把配置问题当成线路问题去换资源。</p>
<h3>备用线路要几条才够？</h3>
<p>答：一般一条热备就够用，关键在于切换是否平滑而不是数量。若账号分布在多个地区，按地区各配一条热备更合理，跨地区的备用线路切换后地址会变，反而增加验证风险。</p>
<h3>心跳间隔设多少合适？</h3>
<p>答：六十到一百二十秒之间。太短会增加无效流量，太长会在 NAT 回收之前没刷新到。可以先设九十秒，观察一周内的断连次数，再按实际回收时间微调。</p>
<h3>并发到底设几个？</h3>
<p>答：从五开始往上加，每次加二，观察失败率。失败率开始抬升的那个值往下退一档，就是这条线路的合理上限。不同运营商差别很大，抄别人的参数往往不合适。</p>
